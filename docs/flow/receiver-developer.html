오류 응답을 API 앞에 두고, 장애 주입은 커밋 경계 이후에 연결합니다.

02 / HTTP INPUT

Gateway outbox의 JSON을 수신합니다

POST /api/v1/quality-events · Content-Type: application/json

{
  "eventId": "00000000-0000-0000-0000-000000000001",
  "source": {"system": "diag-gateway", "resultId": 42},
  "vin": "KMHXX00XXXX000001", "brand": "A",
  "occurredAt": "2026-11-05T23:10:00.000Z",
  "ecus": [{"ecuId": "BMS", "swVersion": "1.2",
            "dtcCodes": ["P0A80", "P0AFA"]}]
}

source의 deviceId·deviceEventId·policyCode와 receivedAt도 받습니다. X-Event-Id와 본문 ID 일치 검사는 하지 않습니다. UUID X-Request-Id는 공통 필터에서 재사용합니다.

03 / VALIDATION

DTO 검증 뒤 ECU·DTC 쌍 중복을 확인합니다

@Valid QualityEventRequest → CasePairValidator → 400 invalid-request

필드검증
eventId / source.resultIdUUID 문자열 / 필수 양수 Long
vin / ecuId / swVersion필수·최대 17 / 필수·최대 30 / 선택·최대 30
occurredAt / receivedAt오프셋 필수 ISO 시각 / 선택, 있으면 같은 규칙
ecus / dtcCodes필수 목록, 빈 배열 허용 / DTC 필수 문자열·최대 10
ECU·DTC 쌍 반복두 번째 이후 위치에 DUPLICATE_CASE

알 수 없는 필드·깨진 JSON·null ECU·숫자 epoch·오프셋 없는 시각은 400입니다. Bean Validation 오류는 중첩 경로로 모두 반환하며, 통과한 요청에 쌍 중복 검사를 수행합니다.

04 / PAYLOAD HASH

객체 키를 정렬하고 원문 시각·배열 순서를 유지합니다

PayloadHasher · 전역 ObjectMapper 설정과 분리한 전용 JsonMapper

01DTO → Map

모든 깊이의 객체를 Map으로 변환, null 생략

02정규 JSON

객체 키 사전순, 공백 없음, 배열 순서 유지

03SHA-256

UTF-8 바이트 → 소문자 hex 64자

두 요청의 차이hash
객체 키 순서 / swVersion null과 생략같음
ECU·DTC 배열 순서 / 고장코드 변경다름
occurredAt의 .000Z ↔ Z / eventId 대소문자다름

Gateway의 진단 결과 정규화와 규칙이 다릅니다. Receiver는 같은 순간으로 시각을 통일하거나 배열을 정렬하지 않습니다. Gateway는 저장한 payload를 그대로 재전송합니다.

05 / SCHEMA

멱등 키와 품질 건을 별도 테이블로 둡니다

receiver DB · V1__receiver.sql · gateway DB와 독립

테이블저장 내용제약
received_eventevent_id, hash, source_result_id, vin, case_count, received_atevent_id PK · 건수 ≥ 0 · hash 소문자 hex 64자
quality_caseevent_id, vin, ecu_id, sw_version, dtc_code, occurred_atevent_id FK · UNIQUE(event_id, ecu_id, dtc_code)
quality_case_naiveevent_id, ecu_id, dtc_code, created_atid PK · event FK·업무 고유 제약 없음

quality_case는 event_id 단일 FK를 사용합니다. source_result_id는 Gateway 결과의 논리 참조이며 DB 간 FK는 없습니다. 품질 건은 요청 ECU·DTC를 펼친 CaseRow마다 1행입니다.

06 / TRANSACTION

별도 Writer 빈에서 이벤트와 품질 건을 원자적으로 저장합니다

QualityEventService → QualityEventWriter.apply → MyBatis Mapper

INSERT INTO received_event
    (event_id, payload_hash, source_result_id, vin, case_count)
VALUES (#{eventId}::uuid, #{payloadHash}, #{sourceResultId}, #{vin}, #{caseCount})
ON CONFLICT (event_id) DO NOTHING
RETURNING event_id::text;
신규 · RETURNING 1행

품질 건 일괄 INSERT → APPLIED. 빈 CaseRow 목록이면 INSERT를 생략합니다.

기존 · RETURNING 0행

저장 hash·case_count 조회 → DUPLICATE 또는 CONFLICT.

@Transactional(rollbackFor = Exception.class). INSERT 실패 또는 영향 행 수 불일치 시 전체 롤백합니다. RETURNING은 MyBatis select의 affectData=true·flushCache=true로 처리합니다.

07 / CONCURRENCY

동시에 같은 이벤트가 와도 신규 반영은 한 번입니다

PostgreSQL PK 경합 + READ COMMITTED의 문장별 가시성

요청 A요청 B
received_event INSERT 성공같은 PK의 INSERT에서 A 트랜잭션 종료 대기
품질 건 저장 → COMMITON CONFLICT DO NOTHING → RETURNING 0행
APPLIED다음 SELECT로 커밋된 hash 조회 → DUPLICATE

A가 롤백하면 B가 신규 INSERT를 수행합니다. 내용이 다르면 뒤 요청은 CONFLICT입니다. 동시 10건 테스트에서 APPLIED 1·DUPLICATE 9·품질 건 3행을 확인했습니다.

08 / HTTP OUTPUT

신규와 중복은 200, 내용 충돌은 409입니다

성공은 ApiResponse, 오류는 web-support의 RFC 9457 ProblemDetail

200 application/json
{"data":{"eventId":"...","result":"APPLIED","caseCount":3}}

409 application/problem+json
{"type":"urn:diag-receiver:error:event-conflict",
 "status":409,"requestId":"...","errors":[], ...}
상황반환
동일 ID·동일 hash200 DUPLICATE · 저장된 case_count
동일 ID·다른 hash409 EVENT_CONFLICT · 기존 데이터 유지
형식·쌍 중복 / DOWN / 예상 밖 DB 오류400 / 503 / 500

eventId는 요청 문자열을 반환합니다. Gateway는 응답 상태 코드로 분류하며, 409는 NON_RETRYABLE, 5xx는 RETRYABLE입니다.

09 / FAULT CONFIG

chaos 프로필에서만 장애 설정 API를 엽니다

POST /admin/faults → AtomicReference<FaultConfig>

{"mode":"DROP_AFTER_COMMIT","holdMs":15000}
→ 200 {"data":{"mode":"DROP_AFTER_COMMIT","holdMs":15000}}

{"mode":"NONE"}
→ 200 {"data":{"mode":"NONE","holdMs":15000}}
설정계약
modeNONE / DOWN / DROP_AFTER_COMMIT · 필수
holdMs생략 시 15000 · 0~60000
수명과 적용 범위프로세스 메모리 · 이후 대상 요청 전체에 적용
잘못된 입력 / 비 chaos400, 기존 상태 유지 / API 404

FaultState는 항상 존재하고 초기값은 NONE입니다. FaultController와 FaultWebConfig만 chaos 전용입니다. GET 설정 조회 API는 없습니다.

10 / DOWN

인터셉터가 본문 파싱 전에 503으로 거절합니다

FaultWebConfig → FaultInterceptor.preHandle

01RequestIdFilter

요청 UUID를 MDC와 응답 헤더에 설정

02FaultInterceptor

DOWN이면 SERVICE_UNAVAILABLE 예외

03GlobalExceptionHandler

503 application/problem+json 응답

적용 경로

/api/v1/quality-events에만 등록합니다. 깨진 JSON도 DOWN이면 503입니다.

복구 경로

/admin/faults와 /actuator/health는 계속 동작합니다. NONE 전환 후 정상 반영합니다.

DTO 바인딩·서비스·DB 쓰기는 실행하지 않습니다. 서블릿 필터 대신 MVC 인터셉터를 사용해 공통 예외 처리기를 그대로 활용합니다.

11 / DROP AFTER COMMIT

커밋 완료 후 성공 응답을 보류합니다

Writer TX 반환 → 충돌 판정 → 판정 로그 → FaultState.awaitIfDropAfterCommit

단계동작
Writer 반환트랜잭션 COMMIT 완료, DB 커넥션 반환
CONFLICT409 예외 → 보류하지 않음
APPLIED / DUPLICATE판정 로그 → 설정 스냅샷의 holdMs만큼 대기
응답대기가 끝나면 200, 클라이언트가 이미 타임아웃했을 수 있음

기본 holdMs 15초 > Gateway read-timeout 5초. 활성 트랜잭션 안에서 호출하면 IllegalStateException입니다. 인터럽트는 플래그를 복원하며, NONE 전환은 이미 시작한 대기를 취소하지 않습니다.

12 / NAIVE COMPARE

naive에서는 선점과 hash 비교 없이 반복 INSERT합니다

receiver.compare.naive-insert=true · 기본값 false

01공통 검증

DTO·ECU/DTC 쌍 중복 검사는 유지

02applyNaive · TX

quality_case_naive에만 INSERT, 항상 APPLIED

03공통 응답 단계

판정 로그와 커밋 후 보류를 동일 적용

SELECT count(*) FROM (
    SELECT 1 FROM quality_case_naive
    GROUP BY event_id, ecu_id, dtc_code HAVING count(*) >= 2
) g;

3개 품질 건 이벤트를 3회 전송하면 naive 9행·중복 그룹 3개, 기본 모드 3행·중복 그룹 0개입니다. 응답 유실 후 재전송에서도 naive는 APPLIED로 3행을 추가합니다.

13 / LOGS & MDC

커밋 판정은 응답 보류 전에 기록합니다

requestId = Gateway claimToken · eventId = 품질 이벤트 UUID

로그레벨·필드
QUALITY_APPLIEDINFO · caseCount · 비교 모드면 naive=true
QUALITY_DUPLICATEINFO · 저장된 caseCount
QUALITY_CONFLICTWARN · 409 예외 전
FAULT_APPLIEDINFO · mode=DOWN 또는 mode=DROP_AFTER_COMMIT holdMs=...

판정 로그는 요청당 한 줄입니다. 컨트롤러 finally에서 eventId를 제거하고 공통 필터는 requestId를 복원합니다. DOWN은 본문을 읽지 않아 eventId가 비어 있습니다. 판정 로그에 VIN·payload를 넣지 않습니다.
