이 자료의 범위: 진단 결과 수신·검증·저장·조회. 실제 외부 전송 기능은 별도 단계입니다.

01 / BIG PICTURE

단말과 외부 시스템 사이의 접수 창구

ECU는 차량 안의 제어기이며, DTC는 제어기가 관측한 고장코드입니다.

01진단 단말

차량과 ECU별 진단 결과 전송

02Gateway

03저장소

진단 이력 + 최신 상태 + 전송 예약

운영자가 확인하는 것

02 / VALIDATION

잘못된 결과는 저장 전에 안내합니다

검사 순서에 따라 형식 오류, 공통 규칙, 브랜드 규칙을 구분합니다.

형식 확인 · 400

필수 필드, 차대번호 형식, 날짜 형식 등을 확인합니다.

공통 규칙 · 422

ECU는 한 개 이상, 진단 시각은 미래 5분 이내, ECU·고장코드 중복 금지.

브랜드 규칙 · 422

BRAND_A는 모든 ECU의 소프트웨어 버전이 필수입니다. 미등록 브랜드는 기본 정책을 적용합니다.

신규 결과의 공통 위반 또는 브랜드 위반은 해당 단계에서 모두 모아 알려줍니다.

03 / BRAND EXAMPLE

빠진 버전이 두 곳이면, 두 곳을 알려줍니다

BRAND_A의 ECU가 세 개이고 첫 번째·세 번째 버전이 없다면

요청 위치ECU소프트웨어 버전판정
첫 번째VCU없음오류
두 번째BMS1.0통과
세 번째ABS없음오류

422 응답에 ecus[0].swVersion과 ecus[2].swVersion을 함께 표시합니다. 이 요청은 저장되지 않습니다.

04 / RESEND

재전송해도 같은 결과는 한 번만 저장합니다

단말 ID + 단말 이벤트 ID를 접수 키로 사용합니다.

상황응답저장 결과
새 접수 키202 · ACCEPTED결과와 전송 예약 생성
같은 키 + 같은 내용200 · DUPLICATE기존 결과 ID 반환
같은 키 + 다른 내용409 · 충돌기존 결과 유지

필드·ECU·고장코드 순서나 같은 순간을 나타내는 시간대 표기가 달라도 같은 내용으로 인식합니다.

05 / CONSISTENCY

결과와 전송 예약을 함께 저장합니다

중간에 실패하면 이번 요청의 저장 변경을 모두 취소합니다.

01진단 결과

차량·단말·정책·요청 원본

02ECU별 이력

버전과 고장코드

03최신 상태

차량·ECU별 가장 최신 관측

04전송 예약

전송 이벤트와 고정 본문

네 단계가 모두 성공해야 신규 접수 202를 반환합니다. 동시에 같은 요청이 와도 결과는 한 건입니다.

06 / LATE ARRIVAL

과거 진단이 늦게 와도 최신 상태는 유지합니다

이력은 모두 보관하고, 현재 화면에 쓸 최신 상태는 진단 시각으로 결정합니다.

도착 순서실제 진단 시각이력 보관최신 상태
1번째 도착11:00저장11:00
2번째 도착10:00저장11:00 유지
3번째 도착12:00 · 고장코드 없음저장12:00 · 빈 고장코드

같은 진단 시각이면 더 큰 결과 ID를 사용합니다.

07 / CONFIRMATION

접수 후에는 결과 ID로 확인합니다

GET /api/v1/diagnostic-results/{resultId}

진단 내용

차량·브랜드·진단 시각·ECU 버전·고장코드

적용 정책

어떤 정책 버전으로 검증했는지

전송 상태

PENDING / SENT / DEAD, 시도 횟수와 마지막 결과

202는 접수·전송 예약 완료입니다. 초기 상태는 PENDING이며 실제 전송 완료는 SENT로 확인합니다. 전송 워커는 이번 구현 범위 밖입니다.

08 / TRACEABILITY

문제가 생기면 요청 ID로 따라갑니다

응답의 X-Request-Id로 해당 요청의 판정 로그를 찾을 수 있습니다.

01요청 ID

없으면 서버가 UUID 생성

02판정 기록

접수 · 중복 · 충돌 · 거절

03결과 확인

결과 ID로 내용과 상태 조회

요청 ID는 UUID 형식이면 재사용합니다. 판정 로그에는 고장코드 본문을 남기지 않습니다.
