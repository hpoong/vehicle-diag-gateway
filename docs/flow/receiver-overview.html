RECEIVER / OVERVIEW

여러 번 받아도 품질 건은 한 번만

차량 진단 결과를 받는 가상 품질 시스템 · 일반 설명용

받습니다

Gateway가 보낸 품질 이벤트를 확인합니다.

한 번만 반영합니다

같은 이벤트가 다시 와도 품질 건을 추가하지 않습니다.

장애를 재현합니다

응답 유실 뒤 재전송에서도 중복이 생기지 않는지 확인합니다.

현재 구현 범위: 품질 이벤트 수신·검증·저장, 장애 주입, 중복 제거 없는 비교 모드, 판정 로그.

01 / BIG PICTURE

Gateway의 전송을 Receiver가 마무리합니다

두 서비스는 HTTP로 통신하고 각자의 데이터베이스를 사용합니다.

01Gateway

보관한 이벤트를 같은 ID로 전송합니다.

02Receiver

이벤트를 확인하고 품질 건을 저장합니다.

03응답

반영 완료 또는 이미 반영된 이벤트임을 알려줍니다.

Gateway는 보내는 일을, Receiver는 받은 이벤트를 한 번만 반영하는 일을 담당합니다.

02 / QUALITY CASE

고장코드 하나가 품질 건 하나가 됩니다

ECU는 차량 제어기, DTC는 제어기가 관측한 고장코드입니다.

ECU전달된 고장코드생성되는 품질 건
BMSP0A80, P0AFA2건
VCUP00011건
합계이벤트 1개3건

품질 건에는 차량·ECU·소프트웨어 버전·고장코드·진단 시각을 저장합니다. 고장코드가 없으면 생성 건수는 0입니다.

03 / VALIDATION

저장할 수 없는 요청은 먼저 안내합니다

잘못된 요청은 400 응답으로 반환합니다.

필수 값과 형식

이벤트 ID, 차대번호, 진단 시각, ECU와 고장코드 목록 등을 확인합니다.

저장 길이

차대번호 최대 17자, ECU·버전 최대 30자, 고장코드 최대 10자입니다.

중복 품질 건

같은 이벤트 안에 같은 ECU·고장코드 쌍이 반복되면 거절합니다.

소프트웨어 버전은 생략할 수 있습니다. 형식 검증 위반은 위치를 모아 안내하고, ECU·고장코드 쌍 중복은 그다음 단계에서 확인합니다.

04 / THREE OUTCOMES

신규·중복·충돌을 구분합니다

Receiver는 전송 이벤트 ID와 내용 확인값으로 판단합니다.

상황응답저장 결과
처음 받는 이벤트 ID200 · APPLIED이벤트와 품질 건 저장
같은 ID + 같은 내용200 · DUPLICATE기존 품질 건 유지
같은 ID + 다른 내용409 · 충돌기존 품질 건 유지

APPLIED와 DUPLICATE 모두 Gateway에 반영 완료를 확인해 주는 응답입니다. 중복 응답에는 처음 저장한 품질 건수를 돌려줍니다.

05 / ATOMIC SAVE

이벤트 기록과 품질 건을 함께 저장합니다

한쪽만 저장된 상태가 남지 않도록 같은 트랜잭션으로 처리합니다.

01이벤트 기록

처음 받은 이벤트인지 확인합니다.

02품질 건 저장

ECU·고장코드별 품질 건을 만듭니다.

03함께 확정

모두 성공하면 반영 완료를 응답합니다.

품질 건 저장에 실패하면 이번 이벤트 기록도 취소합니다. 동시에 같은 이벤트가 10번 와도 신규 반영은 1번입니다.

06 / RESPONSE LOSS

응답을 못 받아도 이미 저장됐을 수 있습니다

전송 실패처럼 보여도 Receiver의 반영은 끝난 상황을 재현합니다.

순서일어나는 일품질 건수
1Receiver가 이벤트와 품질 건을 저장3건
2저장은 완료했지만 응답을 보류 → Gateway 타임아웃3건
3보류를 해제한 뒤 같은 이벤트를 재전송3건
4Receiver가 DUPLICATE로 확인3건 유지

클라이언트의 타임아웃은 반영 실패를 뜻하지 않습니다. 같은 이벤트 ID로 재전송하면 추가 반영 없이 완료를 확인합니다.

07 / FAULT MODES

장애 모드를 바꾸어 동작을 확인합니다

장애 설정 API는 chaos 프로필에서만 사용할 수 있습니다.

모드품질 이벤트 처리DB 변화
NONE정상 처리신규 이벤트만 반영
DOWN본문을 읽기 전에 503 반환없음
DROP_AFTER_COMMIT반영 후 성공 응답을 일정 시간 보류커밋 완료

DOWN 중에도 health 확인과 장애 설정 변경은 가능합니다. 기본 보류 시간은 15초이며, 설정을 바꾸어도 이미 시작한 보류는 끝까지 진행합니다.

08 / CONTROL GROUP

중복 제거가 없으면 재전송마다 쌓입니다

같은 이벤트에 품질 건 3개가 있고, 이를 3번 보낸 비교입니다.

모드매 요청의 결과최종 품질 건중복 그룹
기본 모드APPLIED → DUPLICATE → DUPLICATE3행0개
naive 비교 모드APPLIED → APPLIED → APPLIED9행3개

naive는 중복 제거 없는 비교 실험용 설정입니다. 검증과 장애 처리는 같으며, 별도 비교 테이블에 저장합니다.

09 / TRACEABILITY

요청 ID로 반영 결과를 찾습니다

같은 이벤트를 재전송해도 요청마다 시도를 구분할 수 있습니다.

eventId

어떤 전송 이벤트인지 식별합니다. 재전송에서도 같은 값을 씁니다.

requestId

이번 요청을 식별합니다. Gateway가 보낸 UUID를 그대로 사용합니다.

판정 로그

반영·중복·충돌과 적용한 장애 모드를 기록합니다.

판정 로그에는 차량 차대번호와 요청 본문을 남기지 않습니다. DOWN은 본문을 읽지 않아 eventId가 비어 있습니다.

10 / VERIFICATION

동시 요청과 응답 유실까지 검증했습니다

2026.11.07 기준 · 단위 테스트 9건, 통합 테스트 25건 통과

반영의 정확성

신규·중복·충돌·빈 목록과 DB 제약을 확인했습니다.

실패 시 정합성

동시 10건, 저장 실패 롤백, 커밋 후 타임아웃과 재전송을 확인했습니다.

비교와 관측

naive 중복 누적, 장애 모드 격리, 로그와 요청 ID 연결을 확인했습니다.

Receiver 자체의 HTTP·DB 검증 결과입니다. Gateway와 실제 Receiver를 묶은 전체 시나리오 검증은 별도 범위입니다.

11 / START

로컬에서 실행하고 확인합니다

Java 17과 Docker가 필요합니다. 기본 포트는 8081입니다.

docker compose up -d --wait postgres
./gradlew :receiver:bootRun

# 상태 확인
# http://localhost:8081/actuator/health

# 장애 실험용 실행
./gradlew :receiver:bootRun --args='--spring.profiles.active=chaos'

Compose는 빈 볼륨에서 receiver DB를 생성합니다. 기존 볼륨에 DB를 추가하는 방법은 루트 README, 상세 동작은 개발자용 자료를 참고하세요.
