# front_v2: 부품 LOT 추적 데모

"고장 난 차들의 공통 부품 LOT를 찾는다"는 이야기 하나만 보여 주는 발표용 화면입니다.
장애 주입·전송 재시도·운영 콘솔 같은 실험 기능은 [front](../front/README.md)에 그대로 있고, 여기서는 다루지 않습니다.

```sh
.venv/bin/python front_v2/server.py      # http://127.0.0.1:8071 (SIM_FRONT_V2_PORT로 변경)
```

준비 과정(venv, JDK, PostgreSQL, bootJar)은 [scripts/README.md](../scripts/README.md)와 같습니다.
상단 막대에 DB·수집 서버(gateway)·품질 시스템(receiver) 상태가 보이고, 하나라도 꺼져 있으면 "서비스 켜기" 버튼이 나옵니다. 이 버튼으로 켜려면 서버를 띄울 때 `JAVA_HOME`이 JDK 17을 가리켜야 합니다.
"데이터 보내기"는 기본으로 로컬 gateway·receiver DB의 업무 데이터를 지우고 새 차량군을 보냅니다("DB 비우고 시작" 체크박스, 기본 켜짐).
끄면 확인창을 거쳐 기존 데이터를 남긴 채 보냅니다. LOT 이름이 매번 같아서 이전 데이터와 함께 집계되고, 숨겨 둔 정답과 숫자가 어긋날 수 있습니다. 로컬 개발 전용이며 `127.0.0.1`에만 바인딩합니다.

## 화면 흐름

| 단계 | 화면 | 말할 내용 (한두 문장) |
|---|---|---|
| 1 상황 만들기 | 차량 수, 결함을 숨길 LOT(기본: 무작위), 결함 정도 | "부품을 6개 LOT로 만들어 차에 달았고, 그중 하나에 결함을 숨깁니다." |
| 2 데이터 수신 | 공장 → 수집 서버 ← 차량 흐름도와 건수, 수집 서버 → 품질 시스템 전달 진행 막대 | "공장에서는 '어느 차에 어느 LOT를 달았나', 차에서는 고장코드가 들어옵니다. 통신 재전송으로 같은 결과가 다시 와도 한 번만 저장됩니다." |
| 3 원인 LOT 찾기 | LOT별 고장 비율 막대(원인 후보만 강조), "차 100대로 바꿔 보면" 비교, 정답 공개 | "고장 차량 비율이 다른 LOT보다 크게 높은 LOT가 원인 후보입니다. 숨겨 둔 정답과 같은지 공개해 봅니다." |
| 4 점검 대상 차량 | 그 LOT가 지금 달려 있는 차량 수, 최근 P0700 나온 차 / 아직 안 나온 차 비율, 차량 목록 | "원인 후보 LOT가 지금 달린 차를 골라냅니다. 이미 부품을 교체한 차는 뺍니다." |
| 5 믿을 수 있나요? | 같은 진단 결과 전부 재전송 → 저장 건수·고장 차량 수 비교 | "같은 데이터를 다시 받아도 숫자가 그대로입니다. 그래서 이 숫자로 판단할 수 있습니다." |

화면 아래에는 두 부분이 더 있습니다.

- **DB에 실제로 쌓인 데이터:** 수집 서버 DB와 품질 시스템 DB의 표별 건수, 최근 행(생산 이력·진단 결과·품질 시스템이 받은 고장)을 2초마다 다시 읽어 보여 줍니다. "DB 비우기"로 업무 데이터를 지웁니다(표 구조는 유지).
- **용어 한눈에 보기:** 화면 곳곳의 점선 밑줄 용어(LOT, 고장코드, TCM, VIN, 역추적, 순추적 등)와 같은 설명을 모아 둡니다. 용어에 마우스를 올리거나 누르면 같은 설명이 뜹니다.

## 자주 나올 질문

| 질문 | 답 |
|---|---|
| 왜 건수가 아니라 차량 수로 세나요? | 한 차가 같은 고장코드를 여러 번 보내면 건수는 늘지만 고장 난 차는 1대입니다. 재전송이 섞여도 숫자가 부풀지 않도록 차량 기준으로 셉니다. |
| 같은 진단 결과인지 어떻게 아나요? | 단말 ID와 이벤트 ID가 같고 내용(hash)도 같으면 재전송으로 보고 저장하지 않습니다. 키는 같은데 내용이 다르면 409로 거부합니다. |
| 부품을 교체한 차는 어느 LOT로 세나요? | 장착·탈거 기간을 보관합니다. 고장 차량은 처음 고장이 난 시각에, 정상 차량은 마지막 진단 시각에 달려 있던 부품의 LOT로 셉니다. |
| LOT 기록이 없는 차는요? | 어느 LOT에도 억지로 넣지 않고 "LOT 미확인·이력 없음·이력 모호"로 따로 셉니다. |
| 품질 시스템(receiver)이 꺼지면 추적이 안 되나요? | 됩니다. 추적은 수집 서버 DB의 진단 결과와 생산 이력으로 계산합니다. 품질 시스템 전달만 멈추고, 화면의 전달 막대에 그대로 드러납니다. |
| 1위 LOT가 곧 원인인가요? | 아닙니다. 원인 후보입니다. 진단 차량이 20대 미만인 LOT는 "표본 부족"으로 표시합니다. 결함 정도를 '약함'으로 두면 우연한 고장과 구분이 어려워질 수 있습니다. |
| 정답은 어떻게 검증하나요? | 시뮬레이터가 실제로 보낸 생산 이력과 진단 결과만으로, SQL과 별도로 Python에서 같은 규칙으로 다시 계산합니다. LOT별 고장·진단·장착 차량 수를 그 값과 비교합니다. |

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/ready` | DB·gateway 실행 여부 |
| POST | `/api/prepare` | 꺼진 서비스(postgres·receiver·gateway)만 켬 |
| POST | `/api/run` | (reset이면 DB 초기화) → 차량군 전송 → 역추적. 본문 `{vehicles, defectLot, severity, noise, reset}`, reset 기본값 true |
| GET | `/api/forward?lot=` | 순추적과 정답 |
| POST | `/api/replay` | 저장된 진단 결과를 전부 다시 보내고 저장 건수·추적 결과 비교 |
| GET | `/api/db` | 두 DB의 표별 건수와 최근 행 |
| POST | `/api/reset` | 두 DB의 업무 데이터 삭제 |

고정값: ECU `TCM`, 고장코드 `P0700`, LOT 6개, 차량당 진단 2회, 재전송 30%, 정상 LOT 고장률 2%.
결함 정도는 결함 LOT의 고장률(약함 15% · 보통 40% · 강함 70%)입니다.
"현실 데이터처럼 섞기"를 켜면 LOT 기록 누락 3%, 부품 교체 5%, 이력 없음 1%가 들어갑니다.
